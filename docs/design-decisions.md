# 주요 판단 기록

이 프로젝트에서 내린 판단 중 무엇을 잃는지 알면서 고른 것들을 모았다. 사례마다 문제, 고려한 안, 잃는 것, 고른 것과 이유, 결과와 근거 순서로 적는다. 나중에 바꾼 판단은 바꾼 이유도 적는다.

고려한 안과 트레이드오프는 상당수 AI 코딩 에이전트가 정리해 냈다. 그 안을 고르거나 되묻고 바꾼 것, 그리고 결과를 받아들일지 정한 것은 저장소 주인인 내가 했다. 문제를 내가 먼저 찾은 사례는 그렇다고 적었다.

## 1. 공개 데모는 읽기 전용 계정 하나만 연다 (2026-11-20)

**문제.** 채용 담당자가 직접 눌러 볼 수 있어야 하지만 공개 인터넷에 쓰기 권한을 열면 누구나 인시던트 상태와 판정을 바꿀 수 있다.

**고려한 안.**
- 분석가 권한 계정을 공개하고 데이터를 주기적으로 초기화한다.
- 관리자 TOTP 로그인까지 체험할 수 있게 연다.
- 조회자(`VIEWER`) 계정 하나만 열고 쓰기 흐름과 보안 기능은 글과 그림으로 보인다.

**잃는 것.** 방문자는 담당 지정, 상태 변경, 에스컬레이션 결정, 관리자 화면을 직접 해 볼 수 없다.

**고른 것.** 조회자 계정 `demo` 하나만 활성으로 두었다. 방문자가 데이터를 바꿀 수 없으니 초기화나 운영 부담이 없고 조회자에게 적용되는 개인정보 마스킹을 그대로 보여 줄 수 있다. 분석가·관리자 화면은 같은 데이터를 복원한 로컬 스택에서 찍어 README에 넣었다.

**결과·근거.**
- 계정 시드가 `demo`만 활성으로 두고 나머지 계정은 비활성으로 만든다: `docker/portfolio/seed/seed_demo.py`.
- `demo`의 열람 범위는 공개해도 되는 캡처(`cic17-*`, `syn1-*`, `lab-20261119`)뿐이고 시험 캡처를 직접 조회하면 `403`이다: [`docs/portfolio-deployment.md`](portfolio-deployment.md) 4.4 체크리스트, `scripts/portfolio-verify.ps1`.

## 2. 비밀번호를 공개한 계정의 잠금 문제 (2026-11-20, 2026-11-21에 바꿈)

**문제.** 앱은 비밀번호를 5번 틀리면 계정을 15분 잠근다. 그런데 `demo` 비밀번호는 공개 정보라서 누구든 일부러 5번 틀려 데모를 15분씩 막을 수 있다. 계정 잠금이 보호 효과 없이 방해 수단이 된다.

**처음 고른 것 (2026-11-20).** 앱 코드를 바꾸지 않으려고 공개 스택에서만 환경 변수로 잠금을 사실상 끄고 로그인 요청은 WAF에서 IP당 속도 제한(분당 10회, 버스트 5)으로 막았다. 대안이었던 "앱에 잠금 예외 계정 설정 추가"는 이때는 고르지 않았다.

**잃는 것.** 공개 스택의 다른 계정(지금은 비활성인 분석가·관리자 계정)도 잠금 보호를 함께 잃었다.

**바꾼 것 (2026-11-21, `T29`).** 잠금 예외를 계정 단위로 고를 수 있게 만들었다. 설정에 적은 계정 중 지금 역할이 조회자인 계정만 잠금 검사에서 빠진다. 분석가·관리자는 설정에 적어도 잠금이 유지된다. 실패 기록과 감사 로그는 그대로 남고 막는 일은 IP별 로그인 속도 제한이 맡는다. 처음 방식은 `demo` 하나를 지키려고 공개 스택의 모든 계정에서 잠금을 끈 것이라 범위가 넓었다. 처음에 미뤘던 대안(계정 단위 예외)을 만들어 비밀번호를 공개한 조회자 계정 `demo`만 빼고 나머지 계정은 5회·15분 잠금으로 되돌렸다.

**바꾼 뒤 잃는 것.** 공개 스택의 분석가·관리자 계정은 남의 시도로 15분 잠길 수 있다. 지금은 비활성이라 영향이 작아서 이것은 받아들였다.

**결과·근거.**
- 판정 코드: `src/main/java/com/zeekad/dashboard/security/DashboardAuthenticationProvider.java`(조회자만 제외), 시험 `T29LockoutExemptIntegrationTest`.
- 공개 스택 설정: `compose.portfolio.yml`의 `DASHBOARD_MAX_FAILED_ATTEMPTS: "5"`, `DASHBOARD_LOCKOUT_EXEMPT_USERNAMES`(기본 `demo`), `.env.portfolio.example`의 `PORTFOLIO_LOGIN_RATE=10r/m`·`PORTFOLIO_LOGIN_BURST=5`.

## 3. ZAP "Low 0" 기준과 SPA CSRF 쿠키의 충돌 (2026-11-20)

**문제.** 보안 스캔 기준을 OWASP ZAP High·Medium·Low 모두 0으로 정했다. SPA로 바꾼 뒤 ZAP이 `XSRF-TOKEN` 쿠키에 HttpOnly가 없다는 Low 경고(`10010`)를 냈다. 이중 제출 CSRF 방식은 JavaScript가 이 쿠키를 읽어 헤더로 보내야 하므로 HttpOnly를 붙이면 모든 쓰기 요청이 실패한다.

**고려한 안.**
- ZAP 설정에서 `10010` 규칙 전체를 끈다.
- CSRF 토큰을 쿠키 대신 응답 본문으로 주도록 앱을 고친다.
- 정확히 `XSRF-TOKEN` 쿠키에 대한 `10010`만 예외로 두고 남은 위험으로 적는다.

**잃는 것.** "Low 0"이라는 단순한 기준이 예외 하나를 가진 기준이 된다. 규칙 전체를 끄는 쪽이 편했지만 그러면 다른 쿠키(예: 세션 쿠키)의 HttpOnly 누락도 함께 놓친다.

**고른 것.** 스크립트가 ZAP 결과 JSON을 읽어 모든 인스턴스의 대상이 정확히 `XSRF-TOKEN`인 `10010`만 허용하고 다른 쿠키가 섞이거나 다른 Low·Medium·High가 하나라도 있으면 실패로 판정하게 했다. 이 쿠키는 세션 자격 증명이 아니고 CSP `script-src 'self'`와 `SameSite=Lax`로 위험을 줄였다. 세션 쿠키 `ZEEKAD_SESSION`의 HttpOnly는 E2E로 따로 확인한다.

**결과·근거.** `scripts/security-scan.ps1`의 ZAP 판정부, [`docs/security-verification-report.md`](security-verification-report.md) 4.3. 최근 실행(`T29`)에서 ZAP High·Medium·Low 0(허용 예외 제외)이다.

## 4. 서버 렌더링에서 React SPA로 바꾸면서 지킨 것 (2026-11-19)

**문제.** 처음에는 서버 세션과 Thymeleaf 서버 렌더링으로 만들었다(2026-11-16). 세션 ID 재발급, CSRF, 쿠키 속성, 출력 인코딩을 가장 빨리 확실하게 채울 수 있어서였다. 그런데 처음 만든 화면을 직접 보니 디자인이 마음에 들지 않았다. 외부에 보일 포트폴리오이기도 해서 보안 관제실 느낌의 화면을 React SPA로 다시 만들기로 정했다. 차트와 KPI, 즉시 필터, QR 코드로 하는 TOTP 등록, 채팅처럼 보이는 Slack 스레드 같은 것들이다.

**고려한 안.**
- Thymeleaf를 유지하고 CSS만 다시 꾸민다.
- Next.js로 옮긴다(Node 런타임 컨테이너가 하나 더 생긴다).
- React SPA로 바꾸되 Spring Boot가 같은 출처에서 정적 파일과 JSON API를 함께 서빙한다.

**잃는 것.** 서버 렌더링이 자동으로 주던 출력 인코딩과 폼 CSRF를 SPA 쪽에서 다시 설계해야 했고 화면·보안 시험을 전면 다시 써야 했다(`T08`~`T10`).

**고른 것.** React(Vite + TypeScript + Tailwind) SPA로 바꿨다. 대신 처음 판단의 장점은 지키기로 했다: 같은 출처의 서버 세션(JWT로 바꾸지 않음), 이중 제출 CSRF, `'unsafe-inline'` 없는 엄격한 CSP, JRE 런타임 컨테이너 하나, 앞단 ModSecurity WAF.

**결과·근거.**
- CSP: `src/main/java/com/zeekad/dashboard/config/SecurityConfig.java`(`script-src 'self'; style-src 'self'`).
- 최종 이미지에 Node·npm이 없음: `Dockerfile` 멀티스테이지, `StaticSecurityAndConfigTest`가 마지막 단계의 `node`·`npm` 부재를 확인한다.

## 5. 대시보드 데이터와 파이프라인 데이터를 계정 단위로 나눈다 (2026-11-17)

**문제.** 대시보드는 zeek_AD 파이프라인 DB를 읽어야 하고 인시던트 상태 변경과 에스컬레이션 결정은 써야 한다. 동시에 대시보드 자체의 사용자·감사 로그를 둘 곳이 필요하다. 대시보드가 뚫렸을 때 파이프라인 데이터까지 바뀌면 안 된다.

**고려한 안.**
- PostgreSQL 컨테이너를 하나 더 둔다.
- zeek_AD DB 안에 대시보드 스키마를 함께 둔다.
- 같은 PostgreSQL 서버 안에 별도 DB를 두고 연결 계정을 셋으로 나눈다.

**잃는 것.** 데이터 소스가 셋이 되어 설정과 시험이 복잡해진다. 쓰기는 DB 함수 두 개로만 하므로 새 쓰기 기능이 필요하면 zeek_AD 쪽 함수가 먼저 있어야 한다.

**고른 것.** 같은 서버 안의 별도 DB(`zeekad_dashboard`, 계정 `dashboard_app`)에 사용자·감사 로그를 두고 zeek_AD DB에는 읽기 전용 계정(`dashboard_ro`, 계약 뷰 `SELECT`만)과 쓰기 함수 전용 계정(`dashboard_rw`, 함수 두 개 `EXECUTE`만)으로 붙는다. 컨테이너를 늘리지 않으면서 쓰기 경계, 마이그레이션 충돌 방지, 인증 정보 유출 범위, 감사 로그 보존 주기를 나눌 수 있다.

**결과·근거.** [`docs/deployment-guide.md`](deployment-guide.md) 2.1, 권한 부여 `docker/verify/init/02-init-zeekad-schema.sql`(`GRANT EXECUTE ON FUNCTION dashboard.transition_incident`, `dashboard.decide_review`), 시험 `DataSourceConfigTest`. 감사 로그 표는 `UPDATE`·`DELETE`를 막는 트리거가 있다(`V1__init_dashboard_auth_audit.sql`, 시험 `AuditLogImmutabilityTest`).

## 6. 역할만이 아니라 캡처 단위로 열람을 막고 역할마다 가린다 (2026-11-17)

**문제.** 역할(조회자·분석가·관리자)만으로 권한을 나누면 같은 역할의 사용자는 모든 데이터를 본다. 인시던트 번호나 작업 ID를 바꿔 넣으면 남의 데이터를 볼 수 있는지(IDOR)도 막아야 하고 IP·계정 이름 같은 개인정보를 누구에게 원문으로 보일지도 정해야 한다.

**고려한 안.**
- 캡처 구분 없이 역할만으로 전체 조회를 허용한다.
- 사용자마다 열람 허용 캡처 패턴을 두고 모든 조회에서 검사하며 조회자에게는 개인정보를 가린다.

**잃는 것.** 모든 조회 경로(목록, 상세, 이웃 이동, 운영 집계, 번호 조회)에 허용 범위 검사와 마스킹을 넣어야 하고 그만큼 시험이 늘어난다.

**고른 것.** 사용자별 허용 캡처 패턴으로 객체 수준 접근을 검사한다. 허용 밖과 존재하지 않는 대상은 같은 `403`으로 답해 존재 여부를 흘리지 않고 IDOR 시도로 감사 로그에 남긴다. 조회자에게는 IP 뒤 두 옥텟과 가명 대응을 가리고 분석가 이상은 원문을 보되 원문 열람을 감사 로그에 남긴다.

**결과·근거.** `CaptureAccessService`, `MaskingService`, 감사 동작 `ACCESS_DENIED_IDOR`. 시험 `IdorAndMaskingIntegrationTest`(허용 밖·없는 캡처와 작업 `403` + 감사, 조회자 마스킹). 공개 스택 리허설은 `demo` 응답(큐·상세·운영) 전체에 가려지지 않은 IPv4가 없는지 확인한다(`scripts/portfolio-verify.ps1` `[3d]`·`[T23d-f]`).

## 7. 실제 데이터를 보고 우선순위 규칙을 다시 정했다 (2026-11-21)

**문제.** 인시던트 목록에 무엇부터 볼지 정하는 자동 우선순위를 넣었다. 처음 규칙은 "경보 발송 대상이거나 모델 2개 이상이 함께 탐지하면 높음"이었다. 실제 데이터로 시험해 보니 높음이 구간당 60~120건이고 중간은 거의 0건이었다. 리포트는 경보 후보에만 생기고 여러 모델이 함께 탐지하는 일이 흔해서 우선순위가 분류 역할을 하지 못했다.

**고려한 안.**
- 처음 규칙을 유지한다.
- 신호의 강도를 다시 나눈다: 경보 발송이나 분석가 판단 대기를 높음으로, 여러 모델 동시 탐지나 AI 리포트 있음을 중간으로 내린다.

**잃는 것.** 여러 모델이 함께 탐지한 인시던트가 높음에서 빠진다. 규칙이 바뀌었으니 화면 설명과 시험도 함께 바꿔야 했다.

**고른 것.** 두 번째 안으로 바꿨다. 같은 실제 데이터로 계산하면 구간당 높음 약 5~10건, 중간 약 60~120건, 낮음 약 160~190건으로 나뉘었다. 규칙은 서버 SQL 한 곳에 두고 화면은 그 값을 그대로 보인다(`T23`).

**결과·근거.** `src/main/resources/mapper/zeekad/read/ZeekadReadMapper.xml`(`unifiedQueueBase`), 규칙 설명 [`docs/ui-terminology.md`](ui-terminology.md) '자동 분류 기준'. 공개 데모 전체 2,180건에서 High 76, Medium 661, Low 1,441건이다(`T29` 공개 확인).

## 8. 관제 실무 기준으로 화면을 덜어 냈다 (2026-11-21)

**문제.** 인시던트 상세에 데이터가 있는 것은 거의 다 보였다. AI 리포트를 만든 요청·응답 모델, 토큰 수, 소요 시간, 입력 버전, 실행 ID, 가명 대응표, 정책 ID, 선택지별 확률 막대, Slack 원본 페이로드까지 있었다. 화면 용어도 내부 이름을 피하려다 "탐지 사건", "판단 요청", "조사 진행"처럼 풀어 쓴 말이 되었다. 둘 다 내가 화면을 보다가 먼저 문제 삼았다. 관제에서 리포트의 응답 모델 같은 것을 볼 필요가 있는지, 관제 용어를 쓰는 편이 더 이해하기 쉽지 않은지 물었다.

**고려한 안.**
- 모든 필드를 남기되 접어 둔다.
- 관제 분석가가 판단하고 조치하는 데 쓰는 정보만 남기고 나머지는 화면에서 뺀다.
- 용어는 풀어 쓴 표기를 유지하거나, 관제에서 그대로 쓰는 말(인시던트, 에스컬레이션, 정탐·오탐, 증적, 종결)로 바꾼다.

**잃는 것.** 파이프라인을 디버깅할 때 보던 정보를 화면에서 바로 볼 수 없다. API 응답에는 남아 있지만 화면은 쓰지 않는다.

**고른 것.** 상세는 판단·조치에 쓰는 정보만 남기고(접어 두지도 않음), 용어는 관제 표준 용어로 바꿨다. 관제에서 그대로 쓰는 영어는 영어로, 한국 관제에서 굳은 말은 그 말로 쓰고 내부 DB·필드 이름은 계속 숨긴다.

**결과·근거.** 남긴 것과 뺀 것의 표: [`docs/ui-terminology.md`](ui-terminology.md) '상세 화면 표시 항목'. 옛 표기가 화면에 다시 나오면 실패하는 회귀 시험: `frontend/src/test/uiTerminology.test.tsx`(`OLD_TERMS`).

## 9. 도메인 없이 공개 주소를 만들었다 (2026-11-20)

**문제.** 공개 데모를 개인 Synology NAS에 올리기로 했다. 따로 산 도메인이 없고 같은 NAS의 기존 포트폴리오가 이미 Synology DDNS 주소와 `443` 포트를 쓰고 있었다.

**고려한 안.**
- Cloudflare Tunnel(도메인이 필요하다).
- 공유기에 포트를 하나 더 연다.
- 같은 주소 아래 경로로 나눈다(`/dashboard`).
- 기존 DDNS의 하위 도메인을 만들고 DSM 역방향 프록시로 호스트 이름별로 나눈다.

**잃는 것.** TLS 종료와 전달 헤더를 DSM에 맡기므로, 대시보드 스택은 DSM이 보내는 헤더를 믿는다는 전제 위에 선다. 그 전제를 지키려고 WAF 포트를 NAS의 `127.0.0.1`에만 묶었다.

**고른 것.** 하위 도메인 `soc.<DDNS 이름>.synology.me`와 DSM 역방향 프록시를 골랐다. 공유기 설정을 바꾸지 않아도 된다. 경로 분리는 DSM 역방향 프록시가 지원하지 않고 SPA가 루트 경로를 전제해서 고르지 않았다.

**결과·근거.** `compose.portfolio.yml`(`127.0.0.1:${PORTFOLIO_HTTP_PORT}:8080`), 전달 헤더 처리 `docker/portfolio/nginx/zeekad-portfolio-http.conf.template`, 절차 [`docs/portfolio-deployment.md`](portfolio-deployment.md) 1.1·4절.

## 10. 다시 빌드해도 고쳐지지 않는 WAF 취약점 (2026-11-22)

**문제.** Trivy가 WAF 이미지에서 `libxml2` HIGH 취약점(`CVE-2026-86144`)을 찾았다. 처음에는 기반 이미지를 다시 받아 빌드하면 고쳐질 것으로 보고 문서에도 그렇게 적었다. 확인해 보니 상류의 최신 `owasp/modsecurity-crs:nginx-alpine`(2026-11-19 게시)에도 취약한 `2.13.9-r2`가 들어 있어 다시 빌드해도 고쳐지지 않았다. 고친 `2.13.9-r3`은 Alpine 저장소에만 있었다. 기반 규칙은 XML Content-Type 요청 본문을 ModSecurity가 `libxml2`로 파싱하게 하므로, 공개 주소에서 로그인하지 않은 방문자도 이 파서에 닿는다.

**고려한 안.**
- 상류가 기반 이미지를 다시 빌드할 때까지 기다리고 문서만 고친다.
- 기반 이미지를 고정하고 그 위에서 `libxml2`만 고친 판으로 올린다.
- 위처럼 올리고 XML Content-Type 요청 본문도 WAF에서 거부한다.

**잃는 것.** 상류가 시험한 조합과 패키지 하나가 달라진다. 기반 이미지를 고정했으므로 새 판은 직접 확인하고 올려야 한다. 상류가 고친 기반을 내면 `libxml2` 올리기 줄을 지워야 한다.

**고른 것.** 기반 이미지를 태그와 digest로 고정하고 `libxml2`만 올렸다. 고친 판이 이미 있고 공개 주소에서 닿는 경로라 상류를 기다리지 않았다. 앱은 JSON 본문만 받으므로 XML 거부도 맞는 방어지만, WAF 정책을 바꾸면 검증 범위가 커져서 이번에는 하지 않았다. 전체 패키지를 올리지 않은 것은 ModSecurity nginx 모듈이 상류가 맞춰 빌드한 nginx 판과 어긋날 수 있어서다. `libxml2`는 하한(`>=2.13.9-r3`)만 걸었다. 정확한 판으로 묶으면 Alpine이 옛 판을 저장소에서 지웠을 때 빌드가 깨지고, 하한을 채우는 판이 없으면 빌드가 실패해 취약한 판이 조용히 남지 않는다.

**결과·근거.** `docker/nginx-waf/Dockerfile`, 정적 시험 `StaticSecurityAndConfigTest`, 기반 올리기 절차 [`docs/deployment-guide.md`](deployment-guide.md) 4.1. 새 이미지와 고정 기반의 패키지 차이는 `libxml2` 한 줄이고 nginx·모듈은 같다. 다시 돌린 Trivy에서 WAF 이미지의 `libxml2` 항목이 사라졌다. 깨진 XML 본문은 WAF가 `400`으로 막고 잘 짜인 XML은 앱까지 간다(E2E `[15]`). 결과는 [`docs/security-verification-report.md`](security-verification-report.md) "최근 검증"에 있다.
